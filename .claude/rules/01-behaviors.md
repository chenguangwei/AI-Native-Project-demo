# 🤖 AI 开发者核心行为规范与质量底线 (Core Behaviors & Guardrails)

> 本规范定义 AI 开发者在项目开发过程中的核心行为准则与质量门禁，旨在确保代码库的稳定性、可读性与安全性。

## 1. 永不静默失败与开发原子性 (Fail-fast & Atomicity)
- **防止上下文幻觉循环**：在多轮对话中，如果用户指出你的代码问题，必须在修复后二次确认该问题已被彻底解决，防止旧缺陷在后续的代码生成中被重新引入。
- **小步快跑，原子提交 (Atomic Commits)**：避免大批量修改。每一项修改只要能在本地自洽跑通，即应组织为最小维度的独立提交，严禁在一次提交中夹带不相关的多项变更。
- **职责聚焦**：除非有明显的性能缺陷或关键 bug，否则在开发特定新功能时，绝对不要顺手去修改、重构与该功能不相关的模块。

## 2. 安全第一与前置校验 (Safety & Security)
- **谨慎执行破坏性操作**：在执行任何涉及删除、覆盖、清理等无法撤销的文件系统或终端指令前，必须仔细审核三遍，确保其不会导致意外的数据丢失或系统损害。
- **零信任输入校验**：系统边界的输入数据永远不可被信任。所有公开或跨层调用的接口必须具备严格的参数前置条件验证。
- **禁止静默异常**：所有的 `try-catch` 或底层错误处理必须显式处理或记录日志，确保上层调用者能接收到明确的反馈，严禁静默吞噬异常。

## 3. 测试驱动开发 (TDD & Verification)
- **测试先行，证据通关**：在编写具体业务逻辑之前，应当先将验收标准翻译为可运行的单元测试占位符或测试草稿。
- **断言拦截门控 (Assertion Guardrails)**：在没有通过对应的自动化验证（如 `test`、`lint`、`build`）并确认结果绿色的情况下，严禁声明任务已完成或在 `active-task.md` 中进行打勾。回复时必须展示验证的 stdout 结果快照。

## 4. Git 提交 Trailer 规范 (Commit Trailers)
为了便于自动化流水线与管理工具的解析，所有的 Commit Message 底部必须基于变更事实追加特定的 Git Trailers 指示符：
- `Constraint:` 标明本次提交是为了满足何种技术或架构约束（例如：`Constraint: 解决 iOS WKWebView 跨域报错`）。
- `Rejected:` 说明在开发过程中尝试过但因各种局限而被弃用的方案与理由。
- `Directive:` 供自动化 CI/CD 或测试 Agent 识别的特定运行指令。

## 5. 模型能力分发与调用决策 (Model Optimization)
在设计方案和自我排查时，根据面临的问题复杂度，合理选择与调用不同能力级别的模型：
- **快速原型与微型修复**：适用于速度优先、单纯的代码搬运与格式修复任务。
- **标准功能开发与代码审查**：使用主力标准模型，负责代码正确性、设计模式应用与安全性基石生成。
- **复杂系统推演与深度调试**：当面临高并发锁死、死锁、复杂系统性故障排查等深度逻辑推演时，建议调用具备最强推理能力的模型（如 Opus 或高阶推理模型）进行推演。
